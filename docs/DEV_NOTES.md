# 구현 선택 기록

각 항목 끝의 `사용자 판단`은 직접 작성한다.

## 1. 공식 안내에 없는 품목의 근거

- 선택한 방법: 구 안내에 없는 프라이팬·아이스팩 등은 재활용품 분리배출 가이드라인을 근거로 규칙을 만들고, 해당 사실을 출처와 주의사항에 표시했다.
- 고려한 대안: 전부 "확인 필요"로 비우기, 블로그 자료 쓰기.
- 이유: 시연 품목이 비면 흐름을 보여 줄 수 없고, 블로그는 공식 출처가 아니다.

사용자 판단: (수용/수정/폐기 — 직접 작성)

## 2. 안내 흐름 상태를 주소에 담기

- 선택한 방법: 품목·답변을 `/guide` 쿼리에 넣는다.
- 고려한 대안: 메모리 저장, sessionStorage.
- 이유: 새로고침해도 유지되고 저장 항목이 늘지 않는다.

사용자 판단: (수용/수정/폐기 — 직접 작성)

## 3. 사진 인식 결과는 메모리에만 보관

- 선택한 방법: 홈에서 인식까지 끝낸 뒤 후보 id만 모듈 변수에 두고 `/identify`로 이동한다.
- 고려한 대안: 사진을 sessionStorage에 넣고 `/identify`에서 인식.
- 이유: 사진을 어디에도 저장하지 않는다는 원칙을 지킨다. 새로고침하면 후보가 사라지고 검색 화면이 나온다.

사용자 판단: (수용/수정/폐기 — 직접 작성)

## 4. AI 응답을 구조화 출력으로 받기

- 선택한 방법: Claude API의 `output_config.format`(JSON 스키마)을 쓰고, 서버에서 다시 검증한다.
- 고려한 대안: 프롬프트로만 JSON을 요구.
- 이유: 형식 오류를 줄이되, 지시서대로 사전에 없는 id를 버리는 검증은 유지한다.

사용자 판단: (수용/수정/폐기 — 직접 작성)

## 5. 해석 API의 입력을 id로 받기

- 선택한 방법: 클라이언트는 품목·질문 id와 답변만 보낸다.
- 고려한 대안: 질문 텍스트와 선택지를 그대로 전송.
- 이유: 공개 API를 임의 용도로 쓰는 일을 줄인다.

사용자 판단: (수용/수정/폐기 — 직접 작성)

## 6. 규칙 데이터 값 표기

- 선택한 방법: 수거함 이용 시간처럼 공식 안내에 없는 값은 "확인 필요"로 두고 화면에서 강조한다.
- 고려한 대안: 해당 칸 숨기기, "상시"로 적기.
- 이유: 지어낸 값을 넣지 않는다는 원칙을 지키고, 사용자가 문의해야 할 항목을 알 수 있다.

## 7. `cacheComponents` 끄기

- 선택한 방법: 프로젝트 템플릿 기본값을 끈다.
- 고려한 대안: 켜 둔 채 화면마다 상태를 수동 초기화.
- 이유: 켜면 이전 경로의 화면 상태가 남아 새 사진에 지난 답변이 보인다. 이 앱에는 얻는 이점이 작다.
